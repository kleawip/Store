## 2. Conventions

- **Base URL:** `{API_ORIGIN}/v1`. Storefront routes are under `/v1/store/*` and admin routes under `/v1/admin/*`. Admin routes always need an authenticated staff session with the right role.
- **Format:** JSON, UTF-8. Field names use `camelCase`. Timestamps are ISO 8601 in UTC (`2026-09-25T09:30:00Z`). The admin UI shows them in Asia/Kolkata.
- **Money:** an object `{ "amount": 49900, "currency": "INR" }`, where `amount` is an **integer number of paise**. Never send floats. The UI formats the value; the API sends no formatted strings.
- **Prices not yet approved:** `price` is `null` and `priceStatus` is `"pending"`. The UI must show a neutral "price coming soon" state and must not guess a price.
- **IDs:** see §3. Every ID is an opaque string. The frontend must not parse IDs or derive meaning from them.
- **Pagination:** cursor-based, `?limit=` (default 24, max 100) and `?cursor=`. The response includes `"page": { "nextCursor": "…" | null }`.
- **Errors:** [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) `application/problem+json`, always carrying a stable machine `code`:

```json
{
  "type": "https://api.kleawip.example/problems/validation",
  "title": "Validation failed",
  "status": 422,
  "code": "VALIDATION_FAILED",
  "detail": "One or more fields are invalid.",
  "errors": [{ "path": "lines[0].quantity", "code": "QUANTITY_EXCEEDS_STOCK", "message": "Only 3 left." }],
  "requestId": "req_01J…"
}
```

  The UI branches on `code` only, never on `title` or `message`. The codes defined so far are listed in §8.
- **Idempotency:** every `POST` that creates money, stock or order effects requires an `Idempotency-Key` header (a UUID generated by the client). A repeated key with the same body replays the original response. The same key with a different body returns `409 IDEMPOTENCY_CONFLICT`.
- **Caching:** public catalogue and campaign reads send `ETag` and `Cache-Control: public, max-age=60, stale-while-revalidate=300`. Anything tied to a session sends `private, no-store`.
- **Demo data:** every seeded demo record carries `"isDemo": true`, and the storefront should label it. Demo records never exist in the production database.

## 3. Catalogue data model and stable IDs

```text
Category 1─* Product 1─* Variant (= purchasable SKU) *─1 InventoryItem
                  │            │
                  └─* Media ───┘ (media can belong to the product or to a specific option value)
```

| Entity | Public ID | Notes |
| --- | --- | --- |
| Category | `slug`, e.g. `automotive` | Uses the same slugs as the storefront (`automotive`, `bath`, `household`, `personal`, `pet`). |
| Product | `slug`, e.g. `twisted-loop-1200` | Uses the same slugs as `catalogue.json`. This is the item customers browse; it is **not purchasable on its own**. |
| Variant | `sku`, e.g. `KLW-TL1200-4060-BLU-P2` | The **only purchasable unit**. The cart, wishlist, orders and stock all refer to the SKU. SKU format is TBC with the client. |
| InventoryItem | internal `inv_…` | The physical stock-keeping item that stock counts are kept against. |
| Offer / Campaign / Ribbon | `off_…`, `cmp_…`, `rib_…` | Opaque IDs. |

Once published, a slug is fixed. If a slug has to change, the old slug returns `301` to the new one so saved links keep working.

**Options.** A product declares option groups, for example `size`, `gsm`, `colour` and `pack`. Each variant has exactly one value per group. The API lists only **valid combinations**. The UI must never assume that every possible combination exists.

**How pack quantity affects stock (proposed; TBC):** each variant has `packQuantity` (default 1) and one `inventoryItemId`.
- *Shared units (proposed default):* a pack-of-3 variant draws on the same InventoryItem as the single variant. Selling one pack deducts 3 units. The available pack count is `floor(unitsAvailable / packQuantity)`.
- *Pre-packed stock:* if Kleawip stocks physically sealed packs, the pack gets its own InventoryItem, with `packQuantity` still set so the per-unit price can be shown.
- The client decides which model applies to each product. Both work with the same API shape.

**Price, MRP and tax:** each variant has `price` (the selling price, tax-inclusive, TBC), `mrp` (optional; the UI shows a strike-through only when `mrp > price`), `taxRatePercent` and `hsnCode`. `unitPrice` equals `price / packQuantity` and is computed by the server. Prices are never read from the browser.

## 4. Storefront endpoints — Milestone 1 (catalogue and campaigns)

These are public and read-only. They return **published** records only.

### `GET /v1/store/categories`

```json
{ "data": [ { "slug": "automotive", "title": "Automotive Care", "note": "Wash, dry & detail", "tone": "automotive", "productCount": 3 } ] }
```

### `GET /v1/store/products`

Query parameters: `category`, `q`, `sort` (only `featured` today; `newest`, `price_asc` and `price_desc` are reserved and return `422` with `errors[0].code = "unsupported_sort"`), `limit`, `cursor` (bound to the filters it was issued for; reusing it with different `category`/`q`/`sort` returns `422 cursor_filter_mismatch`). The response also carries `totalCount`, `facets` and a `badge` per item (§11).

```json
{
  "data": [
    {
      "slug": "twisted-loop-1200",
      "title": "Twisted Loop Drying Towel",
      "detail": "1200 GSM twisted-loop microfiber",
      "category": "automotive",
      "spec": "1200 GSM",
      "images": [ { "url": "https://cdn…/twisted-loop-1200-1.webp", "alt": "…", "width": 1200, "height": 1200 } ],
      "priceFrom": { "amount": 49900, "currency": "INR" },
      "priceStatus": "approved",
      "availability": "in_stock",
      "isDemo": false
    }
  ],
  "page": { "nextCursor": null }
}
```

`availability` takes one of `in_stock`, `low_stock`, `out_of_stock` or `not_for_sale`. `not_for_sale` means the product is shown but no approved SKU can be bought yet. **This is the value for every product until Phase 0 approves variants.** `priceFrom` is `null` while prices are pending.

### `GET /v1/store/products/{slug}`

This returns everything the reusable product template needs.

```json
{
  "slug": "twisted-loop-1200",
  "title": "Twisted Loop Drying Towel",
  "category": { "slug": "automotive", "title": "Automotive Care" },
  "summary": "…approved copy…",
  "images": [ { "id": "med_1", "url": "…", "alt": "…", "width": 1200, "height": 1200, "optionValue": null } ],
  "optionGroups": [
    { "code": "size",   "label": "Size",   "values": [ { "code": "40x60", "label": "40 × 60 cm" } ] },
    { "code": "colour", "label": "Colour", "values": [ { "code": "blue", "label": "Blue", "swatch": "#1F4E8C" } ] },
    { "code": "pack",   "label": "Pack",   "values": [ { "code": "p1", "label": "Single" }, { "code": "p2", "label": "Pack of 2" } ] }
  ],
  "variants": [
    {
      "sku": "KLW-TL1200-4060-BLU-P1",
      "options": { "size": "40x60", "colour": "blue", "pack": "p1" },
      "packQuantity": 1,
      "price": { "amount": 49900, "currency": "INR" },
      "mrp":   { "amount": 59900, "currency": "INR" },
      "unitPrice": { "amount": 49900, "currency": "INR" },
      "priceStatus": "approved",
      "availability": "in_stock",
      "maxOrderQuantity": 10,
      "imageIds": ["med_1"]
    }
  ],
  "defaultSku": "KLW-TL1200-4060-BLU-P1",
  "specifications": [ { "label": "GSM", "value": "1200" } ],
  "contentSections": [ { "code": "care", "title": "Care", "bodyHtml": "…sanitised…" } ],
  "related": [ "microfiber-wash-mitt" ],
  "isDemo": false
}
```

**No approved SKU yet:** the response is `variants: []`, `defaultSku: null`, `priceFrom: null`, `priceStatus: "pending"`, `availability: "not_for_sale"`. The UI shows the product without purchase controls.

UI rules that come from this shape:
- The selected combination maps to exactly one entry in `variants`. If none matches, the combination is unavailable.
- `imageIds` sets which gallery images show for the chosen variant. An empty list means the product images are shown.
- The UI shows exact stock counts **only** when `availability` is `low_stock`, using an extra `stockLeft` field that the server returns only in that state.
- `maxOrderQuantity` is the upper limit for the quantity stepper; the server checks it again.
- Shipping serviceability, offers and reviews are **not** part of this response. They get their own endpoints in later milestones, and until then the UI shows neutral states.

### `GET /v1/store/search/suggest?q=bath&limit=6`

```json
{
  "query": "bath",
  "suggestions": [
    { "kind": "category", "label": "Bath Towels", "href": "/shop/bath", "thumbnail": null },
    { "kind": "product", "label": "…", "href": "/product/…", "thumbnail": { "url": "…", "alt": "…" } }
  ]
}
```

- Results are one flat list: categories first, then products ranked as in §11 Q5. `limit` applies to the whole list (default 6, max 10).
- A `q` shorter than 2 characters returns `suggestions: []`.
- Only published products appear.
- The full results page reuses `GET /v1/store/products?q=`.

This returns the whole homepage in one call.

```json
{
  "ribbon": [ { "id": "rib_1", "text": "Explore the Kleawip microfiber collection", "href": "/shop" } ],
  "heroSlides": [
    {
      "id": "cmp_1",
      "eyebrow": "AUTOMOTIVE CARE",
      "headline": "For every detail of the drive.",
      "description": "…",
      "cta": "Explore the drying towel",
      "alt": "…",
      "href": "/product/twisted-loop-1200",
      "images": {
        "desktop": { "url": "…", "width": 1920, "height": 680 },
        "tablet":  { "url": "…", "width": 1200, "height": 700 },
```

## 5. Admin endpoints — Milestone 1 (outline)

Every admin route needs a staff session and a role. Every write records an audit entry with actor, timestamp, before and after values. Proposed roles (TBC): `owner`, `catalogue_manager`, `marketing_editor`, `operations`, `support`, `viewer`.

| Area | Endpoints | Roles |
| --- | --- | --- |
| Categories | `GET/POST /v1/admin/categories`, `PATCH /v1/admin/categories/{slug}` | owner, catalogue_manager |
| Products | `GET/POST /v1/admin/products`, `GET/PATCH /v1/admin/products/{slug}`, `POST …/{slug}/publish`, `POST …/{slug}/unpublish` | owner, catalogue_manager |
| Variants | `GET/POST /v1/admin/products/{slug}/variants`, `PATCH /v1/admin/variants/{sku}` | owner, catalogue_manager |
| Media | `POST /v1/admin/media` (signed upload), `PATCH/DELETE /v1/admin/media/{id}` | owner, catalogue_manager, marketing_editor |
| Inventory | `GET /v1/admin/inventory`, `POST /v1/admin/inventory/{inventoryItemId}/adjustments` (reason required) | owner, operations |
| Import | `POST /v1/admin/imports/catalogue` → validation report; `POST …/{importId}/commit` | owner, catalogue_manager |
| Hero slides | `GET/POST /v1/admin/campaigns/slides`, `PATCH …/{id}`, `POST …/{id}/publish`, `POST …/reorder` | owner, marketing_editor (publishing rights TBC) |
| Ribbon | `GET/POST /v1/admin/campaigns/ribbon`, `PATCH …/{id}`, `POST …/reorder` | owner, marketing_editor |
| Audit | `GET /v1/admin/audit?entity=&id=` | owner |

Publish validation follows the gate in `PRODUCT_PAGE_ADMIN_MAPPING_SPEC.md` and `HOMEPAGE_CAMPAIGNS_SPEC.md`. For example, a slide cannot be published without all three device images, alt text and a published target. A failed publish returns `422 PUBLISH_BLOCKED`, with an `errors[]` entry for every missing item so the admin UI can list them. Full request and response schemas for admin endpoints will be written into `packages/contract` once Codex's admin screen designs have been reviewed.

### 5.1 Implemented admin API (25 Sep 2026)

Zod schemas: `packages/contract/src/admin.ts`. Admin routes use the product **id** (UUID), not the slug, because the slug can change until first publish.

**Auth (all staff):**
- `POST /v1/admin/auth/login` with `{ email, password }` returns `StaffSession { staff: { id, email, name, role, permissions[] }, csrfToken }` and sets the `klw_admin` cookie (httpOnly, SameSite=Strict, Path=/v1/admin, Secure outside local dev).
- `GET /v1/admin/auth/me` returns the same `StaffSession`.
- `POST /v1/admin/auth/logout` returns `204`.
- **Every non-GET admin request must send `X-CSRF-Token: <csrfToken>`.**
- Sessions end after 30 idle minutes, or 12 hours in total.
- Five failed sign-ins lock the account for 15 minutes (`429 RATE_LIMITED` with `Retry-After`). Wrong email and wrong password get the same message.

**Media library:**

| Endpoint | Permission |
| --- | --- |
| `POST /v1/admin/media` (multipart: `file`, optional `alt`) → 201 `MediaAsset`, or 200 with the existing asset when identical bytes were uploaded before | `media.write` |
| `GET /v1/admin/media?q=&unused=true\|false&limit=&offset=` → `{ data: MediaAsset[], totalCount }` | `catalogue.read` |
| `GET` / `PATCH { alt }` / `DELETE /v1/admin/media/{id}` (delete → 422 `in_use` while `usedBy` is non-empty) | read / `media.write` |

Upload handling:
- Accepts JPEG, PNG or WebP, **identified by the file's bytes**, up to 15 MB and at least 300 px on the shortest side.
- Delivered as WebP: EXIF-rotated, metadata stripped (no GPS), longest edge at most 2400 px, and a content-hashed immutable URL.
- The original is kept privately and never served.
- Locally, files are stored in `services/commerce-api/.data/media` and served at `/media/...`. The production store is a Phase 0 decision, and the server refuses to start in production without one.

**Homepage campaigns** (`HeroSlide`, `RibbonMessage`, `CampaignTargetInput` in `packages/contract/src/admin.ts`):

| Endpoint | Permission |
| --- | --- |
| `GET /v1/admin/campaigns/slides` · `GET /slides/{id}` | `catalogue.read` |
| `POST /slides` (`HeroSlideInput` with `internalTitle` required) → 201 draft | `campaigns.write` (owner, marketing_editor) |
| `PATCH /slides/{id}` · `PUT /slides/order { ids }` | `campaigns.write` |
| `POST /slides/{id}/publish` | `campaigns.publish` (**owner only**, TBC) |
| `POST /slides/{id}/unpublish` · `/archive` | `campaigns.write` |
| The same endpoints under `/v1/admin/campaigns/ribbon` (`RibbonMessageInput`: `text` ≤ 120, optional `target`) | as above |

- **Target:** one of `{ type: "product", productId }`, `{ type: "collection", collectionId }`, `{ type: "category", categorySlug }` or `{ type: "page", path: "/shop" | "/bulk" }`.
- **Schedule:** `startsAt` / `endsAt` are ISO strings **with an offset** (e.g. `2026-10-01T09:00:00+05:30`), or null for no limit. Responses give UTC and a computed `state`: `draft | scheduled | live | expired | archived`.
- **Slide publish checklist:**
  - a target is set, and it is published;
  - CTA label;
  - desktop, tablet and mobile images, each at least 75% of its slot (1920×680, 1200×700, 750×900) and within 12% of the slot's shape;
  - alt text for each device;
  - a valid schedule;
  - **no offer or discount wording** (offers arrive in Milestone 2).

  The ribbon checklist covers the target, the schedule and the offer wording.
- Images used by slides appear in the media library's `usedBy` as `hero_slide`, and deleting them is blocked.

**`GET /v1/store/home`** → `HomeResponse { ribbon[], heroSlides[], featuredProducts[] }`:
- Only **live** items appear (published and inside their schedule).
- A slide whose target is unpublished or deleted is skipped. A ribbon message with such a target is shown as plain text (`href: null`).
- Slide images come per device, each with its own `alt`. The top-level `alt` equals the desktop alt.
- `featuredProducts` is the ordered products of the published collection with slug `home-featured`. If that doesn't exist, it's the first 8 published products.

**Catalogue CSV import** (ADMIN_SCREENS_BRIEF §5; `ImportReport`, `IMPORT_COLUMNS` in `packages/contract`), permission `catalogue.write`:

| Endpoint | Result |
| --- | --- |
| `GET /v1/admin/imports/catalogue/template` | A CSV template with 2 labelled DEMO rows |
| `POST /v1/admin/imports/catalogue` (multipart `file`, UTF-8 CSV, ≤ 2 MB, ≤ 2000 rows) | 201 `ImportReport`; **validates only, nothing is written** |
| `GET /v1/admin/imports/catalogue/{id}` | The stored report |
| `POST /v1/admin/imports/catalogue/{id}/commit` | Re-validates against the current catalogue, then applies **all or nothing** → `ImportReport` with `status: "committed"` |

A failed commit returns 422, with `errors[0].code` one of: `already_committed`, `has_errors`, `expired` (over 1 hour old) or `catalogue_changed`.

**Rows:** one row per SKU; rows that share `product_slug` form one product. Product-level cells may repeat, but they must agree. Options go in `optionN_name` / `optionN_value`.

**Cell formats:**
- `price_inr` / `mrp_inr` in rupees (e.g. `499.50`);
- `gst_percent` (e.g. `12`);
- `stock_source`: `own` or `shared:SKU`;
- `opening_stock`: for new own-stock SKUs only; it is recorded as a stock movement.

**Rules:**
- Imports **never publish** and never change published products.
- A blank cell leaves an existing value unchanged.
- An existing SKU's options, stock source and pack size can't change.
- Warnings, such as `price_pending`, don't block an import.
- Every problem is reported with a row number and a column.

| `PATCH /v1/admin/staff/{id} { name?, role?, status: active\|disabled }` | owner | A role change or disable ends that person's sessions immediately. You can't change your own role or status (`self_change`), and the last active Owner can't be removed (`last_owner`). |
| `POST /v1/admin/staff/{id}/setup-link` | owner | The old password stops working and a fresh link is issued. Not allowed for yourself. |
| `POST /v1/admin/auth/setup { token, password }` | **public** (the token is the credential) | 204. Password: at least 12 characters, not containing the email name. The link is single-use. |
| `POST /v1/admin/auth/password { currentPassword, newPassword }` | any signed-in staff | 204; signs out your other sessions |
| `GET /v1/admin/activity?entityType=&actorId=&limit=&before=` | `audit.read` | Store activity log, newest first |

The admin app needs a public `/setup?token=…` page that posts to `/v1/admin/auth/setup`.

**Dashboard:** `GET /v1/admin/dashboard` (any signed-in staff) → `DashboardResponse`:
- `products` counts by status;
- `attention`: products missing a price or images;
- `stock`: low and out-of-stock items;
- `campaignSchedule`: the next 5 campaign starts and ends;
- `recentActivity`: the last 10 events.

### 5.2 Milestone 2: customer accounts (implemented 26 Sep 2026)

Zod: `packages/contract/src/customer.ts`.

**CSRF:** every state-changing `/v1/store/*` request must send `X-Kleawip-Client: storefront`, or it gets 403. Use `credentials: "include"`.

**Sign-in (ADR 0002 R1):** the phone number is the identity, verified by a code over WhatsApp. Email codes are available only for accounts that already have a verified email.

| Endpoint | Notes |
| --- | --- |
| `POST /v1/store/auth/otp/request { phone, channel?: "whatsapp"\|"email" }` | Accepts any Indian mobile format; → 201 `OtpChallenge { challengeId, channel, sentTo (masked), expiresAt, resendAfterSeconds }`. Limits: one code per 30 s and 5 per hour per number (429 `RATE_LIMITED`, `detail` says when). Delivery failure → 503 `DELIVERY_FAILED`. |
| `POST /v1/store/auth/otp/verify { challengeId, code }` | 6 digits, 5-minute expiry, 5 attempts. Errors: `incorrect` (message says the attempts left), `too_many_attempts`, `expired`. → `CustomerSession { customer, isNewCustomer }` and sets the `klw_session` cookie (httpOnly, SameSite=Lax, Path=/, 30 days; ends after 14 idle days). |
| `POST /v1/store/auth/logout` | 204 |
| `GET` / `PATCH /v1/store/me { name?, email? }` | A changed email becomes unverified. |
| `GET` / `POST /v1/store/me/addresses`, `GET` / `PATCH` / `DELETE /v1/store/me/addresses/{id}` | `AddressInput`: Indian mobile, 6-digit pincode, `stateCode` from `INDIAN_STATES`; at most 20 addresses; exactly one default. Another customer's address → 404. |

Development: with no WhatsApp or Resend keys set, codes are written to `services/commerce-api/.data/otp-outbox.log` (git-ignored). Production refuses to start without WhatsApp configured.

**Cart** (guests allowed; checkout needs sign-in). Zod: `Cart`, `CartLine`, `CartLineUpdate`.

| Endpoint | Notes |
| --- | --- |
| `GET /v1/store/cart` | → `Cart { lines[], itemCount, subtotal, gstIncluded, hasWarnings, signedIn }`. Re-priced from the catalogue on every read. |
| `PUT /v1/store/cart/lines/{sku} { quantity }` | Sets an **absolute** quantity (safe to retry); 0 removes. The first add by a guest sets the `klw_cart` cookie. Errors: `PRICE_PENDING`, `SKU_UNAVAILABLE`, `QUANTITY_EXCEEDS_STOCK` / `QUANTITY_EXCEEDS_MAX` ("You can order up to N"). At most 50 different items. → `Cart`. |
| `DELETE /v1/store/cart/lines/{sku}` | → `Cart` |

- Each line reports `quantity` (what was asked for) and `orderableQuantity` (what can be ordered now).
- `warnings[]` is one or more of: `PRICE_CHANGED` (with `previousUnitPrice`), `QUANTITY_REDUCED`, `SKU_UNAVAILABLE`.
- Totals count only orderable quantities.
- Prices include GST; `gstIncluded` is the GST inside `subtotal`.
- At sign-in, the guest cart merges into the account: quantities add up, capped at stock.

**Wishlist** (signed-in):

## 9. Change process

1. The version lives in the URL (`/v1`). Adding a field or endpoint is non-breaking and ships under `v1`. The UI must ignore fields it does not recognise.
2. A breaking change (removing or renaming a field, changing a type or meaning, tightening validation) needs written approval from both builders and the project owner. It ships as a new version, or behind a deprecation period in which both shapes are served.
3. Every contract change updates this file, `packages/contract` and both sides' tests in the same milestone, and adds a line to the changelog below.

## 11. Answers to Codex's frontend data handoff

This section answers the seven questions in `docs/phase-0/FRONTEND_DATA_HANDOFF.md`, and adds the fields that handoff asked for that §4 did not yet cover. Everything here is still **Proposed**.

**Additive fields requested by the handoff:**
- Product list items gain `badge: { "code": string, "label": string } | null`. It is only ever set from an admin-approved badge and never invented; it stays `null` until then.
- `GET /v1/store/products` gains `totalCount` (the number of matches for the current filters) and `facets` (`[{ "code": "category", "values": [{ "value": "automotive", "label": "Automotive Care", "count": 4 }] }]`). Facets for GSM, size and colour appear only once approved variants exist.
- Search suggestions return one flat, ordered list: `[{ "kind": "product" | "category", "label", "href", "thumbnail" | null }]`. The server sets `href`, so the UI never builds a destination itself.

**1. Canonical IDs and URL rules.** Categories and products use lowercase kebab-case slugs (`^[a-z0-9]+(-[a-z0-9]+)*$`). A slug is unique and fixed once published; a later change keeps a `301` from the old slug. Storefront URLs stay `/shop/{categorySlug}` and `/product/{productSlug}`. The selected variant goes in the URL as `?sku={sku}`. SKUs are uppercase, unique, never reused and never derived from option labels. Their format is TBC with the client (§3). Campaign, ribbon and offer IDs are opaque prefixed IDs (`cmp_…`, `rib_…`, `off_…`) and are not used in customer URLs.

**2. Nullable / unknown values, and errors.**

| Unknown or unavailable | Response value | Error code when an action is attempted |
| --- | --- | --- |
| Price not approved | `price: null`, `priceStatus: "pending"` | `PRICE_PENDING` (422) on add-to-bag |
| No approved SKU for the product | `availability: "not_for_sale"`, `variants: []` | `SKU_UNAVAILABLE` (422) |
| SKU out of stock | `availability: "out_of_stock"` | `SKU_UNAVAILABLE` (422) |
| Quantity above stock / above the maximum | — | `QUANTITY_EXCEEDS_STOCK` / `QUANTITY_EXCEEDS_MAX` (422), with `errors[].path` |
| Option combination that does not exist | — | `INVALID_OPTION_COMBINATION` (422) |
| Shipping / COD not integrated | `serviceability: { "status": "unavailable" }` | none; the UI shows the neutral state |
| Offers not configured | `offers: []` | none |
| No genuine reviews | `reviews: null` (the whole block is left out) | none |

**3. Customer vs admin requests.** They use separate sessions:
- The customer session is an httpOnly, Secure, SameSite=Lax cookie `klw_session`, used only for `/v1/store/*`.
- The staff session is a separate httpOnly cookie `klw_admin`, scoped to `/v1/admin`, with a shorter idle timeout. Two-step verification for staff is proposed.
- A customer session is **never** accepted on `/v1/admin/*` (403 `FORBIDDEN`), and neither is an anonymous request (401 `UNAUTHENTICATED`).
- Every state-changing request needs a CSRF token header.
- Proposed role rights (TBC with the client):

| Action | Allowed roles |
| --- | --- |
| Draft products / media | owner, catalogue_manager |
| Publish products | owner, catalogue_manager |
| Draft campaigns / ribbon | owner, marketing_editor |
| Publish campaigns / ribbon | owner (marketing_editor TBC) |
| Adjust stock | owner, operations |
| Refund | owner only (TBC) |
| Audit log | owner |

**4. Media delivery and invalidation.**
- Media URLs are absolute CDN/object-storage URLs. Each file name contains a content hash, so a file never changes behind a URL. The URL can be cached as `immutable` for a year, and editing an image produces a new URL.
- Ordering comes from `position` and is returned already sorted.
- Catalogue and home JSON responses carry an `ETag` and `max-age=60`, so an admin edit shows within about a minute. Publishing also purges the storefront cache: the backend calls a Vercel revalidation webhook with the affected paths. The webhook URL and secret are configured on the server only.
- During the preview the URLs remain relative `/products/…` paths served by the storefront. This changes when object storage is chosen, and it counts as an additive change because the field is still a URL string.

**5. Pagination, search and filters.**
- Pagination is keyset-based with an opaque `cursor`. Results are stable while you page, and a cursor from different filters is rejected with a 422.
- Search is case-insensitive and matches product title, detail/specification and category title. The server treats `%` and `_` as literal characters. Ranking, from first to last: exact title match, title prefix, title contains, other fields. Ties fall back to merchandising `position`. Postgres full-text search with Indian-English synonyms can replace this later without changing the API.
- Filters within one facet are OR, and filters across facets are AND.
- **Drafts cannot reach public search.** Every `/v1/store/*` query is filtered to `status = 'published'` at query level, and a test covers this.

**6. Duplicates and price/stock changes.**
- Order, payment and refund `POST`s require `Idempotency-Key` (§2).
- Cart line updates are `PUT` by SKU and set an absolute quantity, so repeating one is harmless.
- Payment webhooks are deduplicated on the provider event ID.
- Between the product page and checkout, every cart read recalculates from current data and returns `warnings[]` (`PRICE_CHANGED`, `QUANTITY_REDUCED`, `SKU_UNAVAILABLE`). `POST /v1/store/checkout/quote` returns a `quoteId` with a total and a short expiry. Order creation rejects an expired or changed quote with `409` and a fresh quote, so the customer always confirms the amount they are charged. Stock is reserved inside the order transaction.

**7. Blocked on the client. These stay unimplemented, with no invented defaults:**
- SKU format and valid combinations; pack stock model; prices, MRP, GST rate(s), HSN and whether tax is shown inclusive.
- Login method and guest browsing/cart.
- COD and partial-COD rules; shipping provider, serviceability and charges.
- Returns/refund policy; offer and coupon rules; bulk-purchase flow; staff roles; review source.
- Media storage provider.

**First integration test gate.** The backend will supply fixtures that exactly match the gate in the handoff:
- one category listing;
- one product with two SKUs;
- one unavailable SKU;
- a search match and a no-match;
- a draft campaign next to a published one;
- a bag line whose stock has changed.

These fixtures are clearly marked `isDemo` and use neutral placeholder SKUs such as `DEMO-SKU-A`. The handoff asks for "real approved" SKUs, which cannot exist until the client approves them. The gate can therefore pass only as a *mechanics* test until then, and should be re-run with approved data.
